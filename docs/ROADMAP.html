Roadmap

The shared plan for reaching the product described in the README, for people and agents alike. docs/STATUS.md says what works today; this file says what comes next, who owns it and what an agent may pick up; roadmap-history.md keeps what's finished. Rebuilt on 2026-11-02 from main at 2e4afc5, with v0.3.0 the latest release.

How to use this file

  • Each item has an id (R<milestone>.<n>), an owner, a status and a list of pending changes. Pending changes are small, independently mergeable units. Ids are never reused or renumbered: commits, code comments and PRs quote them.
  • Claiming: before you start, put — claimed: <name>, branch <branch> on the pending change and push your branch early (or open a draft PR) so others see it. Don't take a change someone else has claimed. — in PR #n marks one a PR already covers: review that PR rather than starting again. The full working rules are in AGENTS.md ("Working rules", mandatory). Items owned by maintainers are steered by the project maintainers: agents may take their unclaimed pending changes, but design decisions marked decision wait for a maintainer.
  • Finishing: tick the change ([x]) where it is, add the commit or PR, update docs/STATUS.md if what works changed, and add a line to log/devlog.md. Maintainers move ticked lines to roadmap-history.md when a release ships.
  • New work: add a - [ ] line under the item it belongs to; a new item takes the next free id.
  • Status: todo · in progress · blocked (<why>) · done.
  • Follow AGENTS.md (layering, never crash, everything is a tool, platform::process for every external program) and the architecture rules below.

Architecture rules for new work

The project should be easy to fork and bend. New features land behind a seam, not inside a match:

  1. Traits plus a registry, not enums. Target kinds, checks, builders, asset providers and external engines are traits with a registry that holds built-in implementations. Adding one means adding a file and one registration line (as tools already work).
  2. Data over code for catalogues. Stacks, game-engine build recipes, model ids and prices, and engine install pins live in typed tables (or TOML files embedded with include_str!), not in string matches or prompt text.
  3. Headless first; flows are tools. Everything works without the GUI. Anything a person can start from the UI (rebuild, follow-ups, answering questions, engine installs, launching a result) is reachable through Engine::call and the CLI, so MCP, agents, scripts and other frontends get it for free. Orchestration, persistence and process control never live in ui-egui or apps/*.
  4. Versioned files. Every file we write and read back (craft.json, config.toml, project.toml) carries a version, has a JSON schema, and has a migration path.
  5. Structured results. Decisions such as "did the build pass" read typed fields, never English text prefixes.

Open work

Every unticked - [ ] line in this file is open work, under the item it belongs to. cargo xtask pending lists them all, grouped by item (--count for the totals). When you find work that's missing, add it as a - [ ] line under the right item in the same PR, rather than leaving it in a PR description or a chat.

Order and dependencies

Work in phases. Items in the same phase can run in parallel. A phase says what comes first; what stops an item from starting is its Depends on column, which must be done first. A soft dependency should come first but doesn't block. Issues are ranked by people affected and how badly, after leaving out what's already fixed.
