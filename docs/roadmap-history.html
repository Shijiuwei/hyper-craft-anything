R1.2 Check (comparator) trait with structured results

Owner: maintainers · Status: in progress (runtime-visual and behaviour checks: R2.4, R2.5)

  • CheckResult { check, passed, similarity, note, artifacts } replaces note.starts_with("Build succeeded"); older craft.json checks are read compatibly
  • Built-in checks: BuildCheck (per engine recipe) and WebVisualCheck (per width)
  • Web routes (R2.3: every captured page is compared)
  • Widths, thresholds and rounds come from settings ([build]: good_enough, max_rounds, web_widths, max_pages, picture_good_enough); a check may carry its own bar (CheckResult::good_enough)
  • The builder tests its own work during its turn, for every kind: rebuild_check asks the running build (through checks/asks/) to run the same checks as round 0, not counted as a round; refusals for an in-process API builder, whose tools hold the engine
  • What a check couldn't compare is kept (CheckResult::unknowns) and keeps it from being good enough: missing evidence never counts as alike
  • Claims: a check lists what the build must do, each judged on its own (CheckResult::claims); one that fails keeps it from being good enough. Websites claim per page: no sideways scroll where the original has none, no new errors, every file loads, the original's landmarks; and that each of the original's menus and pop-ups opens (page_claims)
  • A windowed app pictured by runtime study claims each of the original's interactive controls (buttons, menus, tabs, check boxes, fields, links; screenshot::INTERACTIVE) by label; text labels stay advisory, since they may hold content the builder replaces
  • Apps and games make claims too: each self-test step of a game (the core loop's, an untested one failing, then the game's own) and each number from the original in the mechanics sheet being used in the code
  • Console apps: with runtime study on, a console original (PE console subsystem) is run with each input in runs::CASES (no arguments, --help, --version) through runtime_walkthrough_record and kept in capture/runs/; RunsCheck runs the rebuild the same way and claims, per input, the same exit and the same output (80% of the words, the programs' own names set aside); the brief asks for a console program instead of a picture
  • Console originals on Linux and macOS: an ELF or Mach-O executable that loads no windowing library (runs::WINDOW_LIBRARIES) is taken for one; on every platform, a program that sat silent and open through every input is treated as windowed after all and pictured instead (ran_like_console)
  • The brief is the builder's own loop for every kind: study overview first, focused follow-ups with the tools, app/UNKNOWNS.md, build, rebuild_check until it would pass, then review the checklist and unknowns before replying
  • The builder's open questions are unknown records (core_unknown_add / core_unknown_edit / core_unknowns_show in the project's investigation folder) instead of a markdown file; its own check lists the open ones and the finished run says how many are left
  • The brief says which toolsets to turn on (enable_toolset: browser, javascript, native, managed, formats) and, for websites, how to study behaviour with the web debugging tools (event listeners, execution, scripted walkthroughs, exported scripts), never pasting the code
  • A console original is rebuilt with the "Rust (console)" stack by default (AppKind::default_stack reads the file); live: a small console tool rebuilt end to end, the builder used rebuild_check and unknown records, and all 6 run claims held
  • Live run where a coding agent uses rebuild_check mid-turn on a game: a request-only snake game in Rust passed build, picture, mechanics and all 5 self-test claims (2 steps of its own)
  • A round's verdict is one line over all its checks and claims (self_check::summary), in the builder's own check and the finished run's status, not the last check's note
