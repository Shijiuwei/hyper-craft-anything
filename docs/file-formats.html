File formats

Every file Craft Anything saves carries a version number. Reading a file runs the same three steps: parse it into a raw document (a JSON value or a TOML table), run the migration steps from the file's version up to the current one, then turn the document into Rust types. The step runner is crates/engine/src/versioned.rs.

A saved User message with pictures is {text, pictures: [paths]}, where the pictures are the copies in the project's attachments/; one without pictures stays the plain string earlier versions wrote.

Other JSON in a project (assets.json, inbox/ except inbox/build-progress.json, checks/, evidence records) has no version yet; add one the first time its shape changes.

Stand-in cached responses

Version 1 stand-in files retain a recorded 304 when no usable cached body was saved. Those samples remain in the file for diagnostics, but replay skips them within the best matching path, query and operation group. If that group has no usable answer, it reports cached_body_unavailable instead of sending a bare 304 to a fresh client. A usable cached body is still stored and replayed as a 200 with was_not_modified: true. This interpretation also applies to existing v1 files; the persisted shape and version are unchanged.

Newer files

A file from a newer Craft Anything is never downgraded or overwritten, because the fields we don't know would be lost. craft.json and config.toml are still read as far as their fields are known, so the person can see their project or keep their settings; every save returns a ToolError that says to update Craft Anything. A newer craft.json whose fields can't be read at all is refused the same way, and a newer config.toml that can't be read gives defaults without touching the file. A newer .cany is refused outright: its evidence layout may have changed in ways we can't see.

A file that can't be parsed is not "newer": config.toml is set aside as config.toml.broken and defaults are used; an unreadable craft.json gives a plain-English error when opened and is left out of the project list.

Adding a migration step

  1. Bump the version constant (MANIFEST_VERSION, SETTINGS_VERSION or FORMAT_VERSION).
  2. Append one function to the matching steps list (MANIFEST_STEPS, SETTINGS_STEPS, FORMAT_STEPS). It takes the raw document from version n to n + 1: rename, move or fill keys. Return Err with a plain-English reason when it can't. A compile-time assertion fails if the list and the constant disagree.
  3. Add a test that reads a literal sample of the old file (keep the existing samples; old files must keep loading forever).
  4. For craft.json, inbox/build-progress.json, mechanics.json and self-test.json, run cargo xtask schemas and commit docs/schemas/. cargo xtask schemas --check (and an engine test) fail when the published schema is stale.
