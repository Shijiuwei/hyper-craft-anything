Rebuild workflow (Study → Build → Check → Refine)crates/ai/src/rebuild/ (kinds, checks and stacks are pluggable: docs/extending.md). Three kinds: website, app, game (a project whose stack is a game engine is always a game). The request decides how to build: a language, framework, engine or platform it names wins over the kind's default stack (Rust + egui for apps, Unity for games, the original's for websites), and the build check, the recorded stack and Play follow what was built (an Electron app opens in its own Electron; a plain static site has nothing to build and passes the build check as it is). Up to 6 refinement rounds, or until a website reaches 90% likeness. A turn cut off by a time limit, crash or dropped connection resumes (up to 3 times); builder turns may run 24 h. Builder retry policy

Builder failures carry a typed reason through Conversation::last_failure. Typed authentication, billing, missing programs, unavailable tools, configuration and unknown protocol failures stop for attention. Transport interruptions, rate limits and nonzero process exits without a typed error get at most three retries; the decision no longer searches English error messages. Structured provider waits win; the earlier numeric “retry in” hint is only a delay fallback after a failure has already been classified as retryable. All waits remain cancellable and bounded to fifteen minutes. Local inbox and workspace write failures are not retried using a concurrent backend failure's retry advice; the original local error is returned. A missing saved session starts afresh only when a fresh request is available; otherwise the run stops without retrying the unavailable session.

Claude Code's failed or unauthenticated craft-anything MCP server in its init event stops the owned CLI process. Pending servers and failures in unrelated optional servers do not stop it. Claude assistant error codes, HTTP status/provider errors and ACP authentication errors retain their typed meanings. A later generic result does not erase a more specific error.

API retries continue the existing history without inserting the user's message again or replaying completed tools. Stateless CLI retries receive the whole original request. OpenCode now uses run --format json: its API error status and retry flag decide retryability while text, tools and usage still reach the feed. Missing or invalid step costs keep the turn's cost unknown; explicit zero remains a known cost. A CLI that fails with only a numeric exit also uses bounded retries; its display error remains available if recovery fails. The process wrapper sends one final turn event and becomes available for the next request.

Protocol fixtures, a loopback HTTP server, scripted API turns and executable CLI stand-ins cover these paths, including cancellation and the retry cap. An executable that exits 1 without a structured error resumes its saved session, while typed setup errors retain priority over the same exit status. No live provider or paid-model run was performed. The separate source of #64's 41 attempts remains unverified.

Packed Bun members with encoding value 2 are labelled utf16le, matching their stored UTF-16LE bytes. Reading or unpacking preserves those bytes. Synthetic graphs cover UTF-16LE (including a surrogate pair), Latin1 and binary members across both supported module-record and offsets-block sizes. Native tool-call stop reasons

Native OpenAI-compatible tool calls retain a reported output limit or refusal instead of replacing it with a tool-use stop. The conversation can therefore reject those calls before running a tool, including calls whose arguments happen to be valid JSON. A normal stop with tool calls still works for servers that omit tool_calls as the finish reason. Calls retained after a pause or another terminal stop get matching non-execution results, so subsequent requests keep valid tool-call history. A pause continues the same turn; terminal stops wait for the next user message. Checked with streamed-call fixtures and HTTP/SSE stand-ins through the real conversation and engine loop. Three history-pairing regressions fail without the follow-up and pass with it. The affected crate's 223 tests and Clippy checks passed locally. No live provider or local-model build was run.

Keep-awake helper cleanup

Rebuilds release their keep-awake guard before emitting Finished and clearing the running flag. The guard waits up to five seconds for the owned helper's supervised cleanup, logging a warning if that deadline passes. Cleanup runs on the rebuild worker, with a bounded shutdown wait.

Checked on Linux with real subprocess stand-ins: dropping a guard closes the helper's listener, a stand-in CLI can drop it and exit immediately without leaving the helper running, and an already-finished helper releases promptly. The immediate-exit case fails with the earlier asynchronous cleanup. The intermittent Windows report and Windows/macOS sleep inhibition have not been rechecked for this change; Windows runtime validation remains on the roadmap.

Tool calls written as JSON

The text fallback accepts complete bare or fenced JSON calls with name and arguments (parameters also accepted), including a function wrapper and JSON-encoded arguments. Automatic recovery also handles these responses when native tool calling was offered. A call must name a tool offered in that turn; ordinary JSON answers and JSON examples surrounded by prose are left as text. Native calls are kept once; text-call recovery skips truncated or refused replies. Complete backtick-fenced legacy ReAct steps remain supported when their body begins with an explicit protocol marker. Both parsers use the same fence boundaries: at least three opening backticks and a standalone closing line of at least that length, with no earlier matching closing fence. Shorter backtick lines inside a longer fence remain content. Ordinary fenced code, malformed fences and non-call JSON objects or examples containing protocol markers remain text; valid call arguments may contain those markers. The parser regressions failed on the previous guards and passed with their corrections. Fenced JSON calls also use these boundaries during automatic recovery and accept only an empty or json info string. Checked with parser fixtures, HTTP/SSE stand-ins exercising real engine tool execution in both protocols, and non-action, stop-reason and duplicate-call controls. No live local-model build was run; other text-call formats remain unsupported.

Linux graphics card choice

On Linux the desktop app draws on the GPU that drives the screen (#571), read from the connected displays in /sys/class/drm: the built-in panel's GPU on a laptop, the only GPU with monitors on a desktop, and the discrete GPU when monitors are on more than one GPU or nothing can be read. WGPU_ADAPTER_NAME and WGPU_POWER_PREF still decide when set. desktop.log says which adapter was chosen and why.

Checked live on one laptop (AMD Renoir iGPU driving the panel, NVIDIA RTX 3050, CachyOS, KDE Plasma on Wayland): the window opens in 3 s on the AMD GPU instead of 18–25 s on NVIDIA, and the desktop no longer lags; WGPU_POWER_PREF=high, WGPU_ADAPTER_NAME=nvidia and DRI_PRIME=1 with WGPU_POWER_PREF=none still draw on NVIDIA. Desktops with monitors on one or two GPUs and Intel laptops are covered by unit tests on fake /sys/class/drm folders only.

Build progress across runs

When app files can be compared, a build stops after two consecutive completed builder turns leave them unchanged. The versioned inbox/build-progress.json record keeps that count when the project is reopened or Try again is pressed. File contents and executable permissions decide progress, so rewriting identical bytes does not reset it. An actual app edit or a new nonempty request starts another attempt, including notes queued during a turn or check and notes consumed by a builder hook. Empty notes and plain Try again keep the saved count. Dependency/build caches, git metadata and Craft's own records, including checks in a project edited in place, do not count. Symlinks are recorded without following their targets. A successful check may still finish the second unchanged turn, and a run waiting only for checks does not start the builder again. Within a run, file digests are reused while size, modification time and executable bits match; Unix file identity and change time also invalidate a cached read. The first scan reads content, but unchanged imported assets are not read again before and after every turn. The metadata is only a cache key: rewriting identical bytes still produces the same content fingerprint. The cache is isolated by project root, drops deleted or retyped paths, and is discarded after scan errors or cancellation. It is not persisted, and the version-1 fingerprint/schema is unchanged. Sockets, pipes and devices contribute their names and types without opening their contents. If a scan cannot finish because of limits, permissions or changing files, the feed says why the unchanged-turn limit is skipped for that run. The saved fingerprint and count are cleared so a later readable run starts a fresh comparison. Checks and the existing round limit still apply. Cancellation still stops the run; completed builder replies are saved as awaiting checks before the post-turn scan. Broken or newer progress records and record-write failures remain errors.

Scripted API turns and executable CLI stand-ins cover the stop, persistence, fresh requests and check recovery. This change has not been verified with a paid model or a live provider. Copying a whole project keeps its progress record; Duplicate creates a new attempt with a fresh conversation and count, as it already does for usage. An existing root-level file or directory named build-progress.json remains app data: it is fingerprinted, copied by Duplicate and kept when Craft's project records are removed. Its JSON shape does not make it a Craft record, and it is never migrated into the inbox.

Notes consumed by builder hooks now only queue a progress reset while the turn is running. The reset is saved after the successful turn and its awaiting_check recovery state are persisted. Multiple consumed notes coalesce into one reset; blank notes do not reset the count. A broken or inaccessible progress record still returns its actual error at that safe boundary, without starting another provider request or losing the finished builder reply. If the turn fails or is cancelled after consuming a note, its reset is saved before the run ends so reopening keeps the new request's full allowance. The original failure or cancellation remains the result; a reset that cannot be saved is reported separately and never overwrites a broken or newer record. Scripted turns cover both outcomes, blank notes and unreadable records.

Local model identifier task hints

Automatic local setup recognizes numeric suffixes on known embedding, reranking and speech task tokens. Generic GGUF filenames (ggml-model-*.gguf, ggml-model.gguf and model.gguf) also keep their immediate model directory as a task hint, with either path separator. Named model files, publisher prefixes and unrelated words are not classified by arbitrary ancestor directories.
